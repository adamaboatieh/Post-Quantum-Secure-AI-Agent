Post-Quantum Secure AI Agent
A focused research prototype that authenticates AI-agent tool actions with Ed25519 or ML-DSA-44, enforces independent authorization, rejects stale and replayed requests, and measures the operational cost of post-quantum authentication.

Problem and research question
An LLM can propose a tool action, but model output is untrusted. A receiving service needs a reliable way to determine that the exact request passed through a trusted signing boundary, was not modified, is fresh, and is permitted.

Is post-quantum cryptographic authentication practical for securing AI-agent actions today, and what operational trade-offs does it introduce?

This repository answers that question with one deliberately small action: read_file for bounded UTF-8 .txt files beneath data/. It is the assignment prototype, not the future Secure Agent Action Gateway product.

Architecture
User
  -> untrusted proposal model
  -> strict structured proposal validation
  -> trusted authorization policy
  -> trusted signer (Ed25519 or ML-DSA-44)
  -> signed action envelope
  -> tool service
  -> signature + freshness + replay + authorization checks
  -> execute or reject
The LLM/model adapter never receives the private key. The trusted signing service owns key use. The tool service resolves verification keys from its own registry and independently applies authorization after signature verification. See Architecture and Threat Model.

Why signatures instead of encryption
Encryption protects confidentiality. It does not, by itself, prove which agent approved a request or whether the request was modified. Digital signatures bind a private key to exact canonical request bytes, providing integrity and origin authentication under the stated key-management assumptions. Payloads in this prototype remain readable; use authenticated encryption or TLS separately when confidentiality is required.

Signature algorithms and agility
Ed25519 is the compact classical baseline: 32-byte public key and 64-byte signature in this implementation. It is not post-quantum secure.
ML-DSA-44 is the FIPS 204 post-quantum signature mode: 1,312-byte public key and 2,420-byte signature. The implementation uses the maintained cryptography library and does not implement cryptographic mathematics.
Both implement the interfaces in src/signing/base.py, sign the same canonical payload, and pass the same security suite. Choose a mode with --algorithm ed25519|ml-dsa or SIGNATURE_SCHEME.

Signed action envelope
The signature covers canonical, domain-separated bytes containing:

protocol and audience;
algorithm, agent ID, and trusted key ID;
UUID request ID and a random nonce;
issue and expiry timestamps;
tool name and arguments.
Objects use sorted compact UTF-8 JSON. Floating-point values are forbidden in the signed profile to avoid number-format ambiguity. The signature remains outside the payload.

Authorization, freshness, and replay protection
Authentication and authorization are separate. Even a correctly signed delete_database request is denied because the assignment policy permits only read_file. The server owns the allowed data/ root and rejects absolute paths, traversal, Windows drive/device forms, links/reparse points, hard links, non-regular files, oversized files, and invalid UTF-8.

Freshness uses issued_at, expires_at, a 60-second maximum lifetime, and limited clock skew. SQLite atomically claims both request ID and nonce, so a captured valid request cannot be accepted twice while replay state is retained.

Prompt-injection limitation
Cryptography does not solve prompt injection. An injected prompt can influence the proposal before it is signed. Strict schema validation and policy can block known forbidden outputs, but a manipulated action that remains policy-valid can still be signed and executed. The seventh attack demonstrates this by accepting a validly signed read of the synthetic confidential.txt fixture.

Quick start
Requirements: Python 3.11+ and a platform where cryptography 50 exposes ML-DSA-44.

Set-Location C:\Users\ADAM\Desktop\Post-Quantum-Secure-AI-Agent
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e .
Run the complete offline demo with both algorithms:

.\.venv\Scripts\pqsa-demo.exe "Read report.txt and summarize it." --algorithm ed25519
.\.venv\Scripts\pqsa-demo.exe "Read report.txt and summarize it." --algorithm ml-dsa
The output shows the natural-language task, strict proposal, selected signature algorithm, request ID, server result, and a compact summary. Private keys are generated in memory for the demo and are never exposed to the model backend.

Tests and attacks
The suite uses the standard library test runner, so no additional test package is required:

.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m attacks.run_attacks --algorithm both
Coverage includes valid and invalid signatures, changed messages, incorrect public keys, malformed model output, expired and future requests, replay, unauthorized actions, HTTP execution, both algorithm modes, and all seven assignment attacks:

message tampering;
signature forgery;
replay;
expired request;
unauthorized action;
prompt injection;
signed malicious-but-valid action.

Regenerate the committed research artifacts:

.\.venv\Scripts\python.exe -m benchmarks.run_benchmarks --repetitions 500 --scales 1,100,1000,10000

Optional live-model demonstration
Use a compatible chat-completions endpoint that supports JSON object output:

$env:PQSA_LLM_URL = "https://your-provider.example/v1/chat/completions"
$env:PQSA_LLM_MODEL = "your-model"
$env:PQSA_LLM_API_KEY = "your-key"
.\.venv\Scripts\pqsa-demo.exe "Read report.txt and summarize it." --backend live --algorithm ml-dsa
Do not commit .env, API keys, or private keys. A provider response is never trusted simply because it came from an LLM API.

Known limitations
The default demonstration is a deterministic proposal model, not a live LLM.
The local HTTP adapter has no TLS; production transport must be authenticated and encrypted.
Replay state is single-host SQLite and does not provide distributed exactly-once execution.
The response is not signed, and logs are not tamper-evident.
Canonicalization is a restricted Python profile, not full RFC 8785.
Filesystem containment narrows but does not eliminate hostile concurrent mutation risk; the trusted data directory needs OS protection.
Python-visible memory measurements do not include every native allocation.
Cryptographic authentication does not prevent prompt injection, malicious model choices, compromised policy, or stolen keys.
Production recommendations
Use an HSM, cloud KMS, TPM-backed service, or isolated signer; implement key rotation and revocation; add TLS and response authentication; use durable distributed replay state and idempotent execution; protect policy and data with OS permissions; add tamper-evident audit; risk-tier actions; require approval for high-impact operations; test the selected live model against prompt and tool-content injection; and independently review the complete system.
